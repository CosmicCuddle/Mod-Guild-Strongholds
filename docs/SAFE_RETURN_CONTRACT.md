# Private-property entry and safe-return contract

**Current status:** Pure C++ state machine and a **test-only** MariaDB contract. Neither a private map nor working teleportation has been implemented. All runtime housing capabilities remain blocked by `StrongholdStartupGate.h`.

## Why this matters

The original AzerothCore teleport API can reject a map because of entry restrictions, map validity or client compatibility, and instance selection is normally player/group based rather than guild based. A successful call to `Player::TeleportTo` is **not** proof that a player has arrived in the intended guild's private instance.

We must never strand characters inside the wrong guild's settlement, leave them on an unavailable map after uninstall, or overwrite their safe departure point.

## The three durable visit states

| State | Meaning | Must happen before |
| --- | --- | --- |
| `prepared` | Original player, guild generation and return location saved in character DB | Requesting any entry teleport |
| `inside` | Actual destination map, guild ownership and privacy verified **after** arrival | Making housing interactions available |
| `returning` | Original return point revalidated and departure requested; still saved | Requesting the exit teleport |

A visit ticket is **removed only after the actual character's safe return has been verified**. If a worldserver crash happens before that confirmation, the ticket remains for later recovery. There is a unique `player_guid` key, so concurrent visits cannot overwrite a player's original location, and a unique opaque `visit_nonce` prevents reuse.

## Admission prerequisites

All must succeed:
1. Module gameplay enabled and actual isolation mechanism **proven**, not guessed.
2. Character's current guild membership confirmed by the server; saved property owner matches guild ID **and** creation date.
3. Property state is active, not archived.
4. Current position captured directly from the server and revalidated against `MapMgr::IsValidMapCoord`, permitted ordinary-world map, and safe landing/collision checks.
5. No outstanding `naxx_gs_visit` ticket exists for that character.
6. A new unguessable nonce is generated by the server, and the ticket is committed durably in the **character DB before the entry teleport**.
7. Verify after teleport completion that the target map instance and private owner are exactly those intended, then mark the ticket `inside`.

No client-supplied guild ID, map ID, coordinates, entry token or gossip string may be treated as authoritative.

## Emergency recovery **must not** depend on access eligibility

A visitor needs an exit even after:
- `NaxxGuildStrongholds.Enabled` switches to 0;
- removal from the guild or a leadership change;
- guild disband / property archival;
- failed or interrupted arrival;
- realm shutdown or crash;
- future property relocation.

Therefore an emergency return uses the persisted visit ticket for **that character**, revalidates it, and does **not** require active guild membership, guild ownership or active housing configuration. It must use a separately guarded recovery hook that remains available when gameplay is disabled.

If the return point cannot be validated, do **not** teleport to arbitrary stored numbers. The eventual runtime code must validate a safe homebind/GM recovery fallback without corrupting normal IP phases. This fallback and logout/login hook integration do **not** exist yet.

## Critical work still absent

- Actual guild private-map instance or phase implementation.
- Real `PlayerScript`/logout/login hooks and teleport acknowledgements.
- Map-instance matching after teleport, actual safe landing, IP phase restoration and no cross-guild visibility.
- Versioned `CharacterDatabase` adapter with prepared/inside/returning compare-and-swap transitions.
- Full integration with installed Playerbots and other modules; module removal while player is inside still requires an **independently tested evacuation plan**.
- In-game tests of disbanding during transport, death/release, transport/taxi, summons, battleground origins, cross-map teleport, downtime and disabled-module recovery.

## Executable development checks

- `tests/visit_recovery_tests.cpp` tests policies, invalid origins, entry gating, version guards, foreign character denial and emergency return even after property archival.
- `tests/mysql_visit_recovery_test.py` runs only against the throwaway `naxx_gs_ci_test` DB and checks durable ticket state, uniqueness, simulated failures/rollback, resuming a return after an archived guild, new connection recovery, identical-schema reinstallation and clearing only after a verified return.
- The CI script uses test fixture coordinates; **no test teleports a real WoW character**.

## Compatibility and rollback

The `naxx_gs_visit` table is **module-owned** and never touches character position columns. A data-preserving uninstall must evacuate/recover any outstanding visitors **before** the compiled module is removed. During normal disable/uninstall, visit tickets are not silently deleted. The *optional destructive purge* is dangerous with outstanding visitors and requires a tested evacuation, backups and explicit approval. No SQL should be applied to the live server at this stage.
